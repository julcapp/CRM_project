# Архитектура CRM v0.1

## Назначение
Одна независимая CRM-платформа для множества проектов. Три уровня: платформа, проект, мероприятие.
- Платформа: identities/people, учётные записи работников, глобальные технические настройки.
- Проект: бренд, настройки форм, участники, команды, роли, интеграции и статистика.
- Мероприятие: название, описание, дата, время, часовой пояс, публичный slug, статусы, индивидуальная ссылка и список регистраций.

## Разделение данных
- people — внутренняя общая личность, без предоставления сотрудникам доступа к чужим проектным данным.
- project_contacts — отдельная карточка участника на каждый проект; UNIQUE(project_id, person_id).
- events, registrations, tasks, notes, integrations принадлежат проекту.
- Пользователь может принадлежать нескольким проектам, но их история и статусы не объединяются в интерфейсе.
- Все операции над проектными сущностями требуют аутентификации и проверки project membership/role на сервере. Проверять принадлежность project_id и event_id, а не доверять клиентским параметрам.
- Для PostgreSQL применять RLS как дополнительную защиту, не как единственную; интеграционные тесты на межпроектную изоляцию.
- Объединение людей по Email допустимо только после подтверждения владения адресом; номера телефонов сами по себе не служат достаточным основанием для склейки. Нужны процедуры разъединения ошибочно объединённых записей.
- Глобальная идентификация НЕ даёт прав на сквозной маркетинг или просмотр данных разных проектов. Согласия и цели обработки учитываются отдельно по проектам.

## Регистрация на мероприятие: 3 пользовательских экрана
1. Экран Email: название/дата/время мероприятия, email, кнопка отправки. Можно подтвердить по 6-значному коду или интерактивной одноразовой ссылке из письма. UI показывает ввод кода и возможность открыть ссылку. Email после проверки получает verified_at.
2. Экран подтверждения: пользователь вводит телефон и выбирает один из двух независимых маршрутов Telegram / MAX. Система создаёт короткоживущую привязку с одноразовым state/token, показывает кнопку перехода в бота. Только подтверждённый webhook/API callback от бота может завершить messenger verification. Простое открытие ссылки не является подтверждением. Связь номера с учётной записью мессенджера подтверждать только при фактическом наличии поддерживаемого механизма получения номера/контакта и согласия пользователя; иначе фиксировать номер как заявленный и требовать отдельного подтверждения или явно изменить требования. Проверить официальные API MAX и Telegram перед интеграцией.
3. Экран результата: подтверждённая регистрация, детали мероприятия, статус выбранного мессенджера. При неполном подтверждении отображать ожидающий статус, не успех.

Email ссылка должна приводить к третьему пользовательскому экрану только после успешной серверной проверки; в общей трёхшаговой схеме это переход к следующему этапу подтверждения телефона/мессенджера, а не выдача статуса «зарегистрирован».

## Безопасность авторизации
- Один вызов выдаёт код и/или ссылку на одну серверную email_challenge; хранить только хэши токенов, ограничить срок действия (например 10 минут), число попыток, частоту отправок и повторные запросы.
- Защита от перебора, email enumeration и replay; атомарное однократное погашение challenge; короткоживущая серверная сессия.
- Для bot deep links — случайный непрозрачный state, TTL, single-use, привязка к event/registration/каналу/сессии.
- Webhook подписывать/проверять в соответствии с документацией провайдера; дедупликация входящих событий.
- Согласия на ПДн/маркетинг разделены, доказательства версий и дат хранятся по проектам и целям. Маркетинговое согласие необязательно для регистрации.
- Журнал аудита изменений ролей, подтверждений, регистраций, удалений и экспортов.
- Секреты только в переменных окружения/секрет-хранилище; логирование без токенов и персональных данных.
- Минимальные сроки хранения и процедуры удаления/экспорта данных; отдельно проверить юридические требования юрисдикций перед эксплуатацией.

## MVP по мотивам amoCRM
- Переключатель проекта и обзор: новые участники, регистрации, ожидают подтверждения.
- Контакты проекта: карточки, поиск и фильтр по статусу.
- Мероприятия: CRUD, дата/время/часовой пояс, уникальная ссылка, список регистраций.
- Простая воронка: email_pending -> messenger_pending -> confirmed -> attended/cancelled; статусы no_show и archived опционально позже.
- Задачи менеджера и небольшие заметки; без сложного конструктора роботов и телефонии.
- Четыре роли: platform_owner, project_admin, manager, viewer.
- Интеграции (email, Telegram, MAX) и аналитика — по мере подключения, с тестовыми адаптерами.

## Технологическая рекомендация
Для локальной разработки на Home-Boss: PostgreSQL, backend API (например FastAPI или NestJS), React/TypeScript, тесты интеграционной изоляции. Конкретный стек окончательно выбрать перед кодированием. PinMe рассматривать как возможный способ публикации клиентской части, а не как обязательную основу CRM или замену серверных мер безопасности.
